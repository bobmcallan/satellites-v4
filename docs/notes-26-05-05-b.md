# Claude session walkthrough — orchestrator friction discovery

A trace of a session that did **not** drive a story to plan-close.
This session probed where the substrate's code shape leaks through
to the operator's workflow, deleted persistent guidance, and
ended with an agreement on what to fix in the seed documents and
the MCP function surface.

Format mirrors `docs/claude_session_walkthrough.md`. Where calls
were made, payloads are abbreviated. Where the operator and
Claude exchanged words instead of verbs, the dialog is the trace.

Every response is labelled **seed** (body comes from a markdown
file under `config/seed/`) or **runtime** (body is a database row
written at request time).

**Source of the block:** `config/seed/artifacts/default_agent_process.md`.
**seed.**

Also loaded into context, outside the satellites surface:

- The user's auto-memory index (`MEMORY.md` + six memory files)
  carried from prior sessions: feedback notes about status
  changes, contract rubric reading, verifying with git;
  project notes about dispatch architecture, ownership tiers,
  context separation.
- Global `CLAUDE.md` collaboration style.

The session is **unbound**: `session_register` has not been
called, no agent doc is stamped on the session, no contract is
attached. From the substrate's perspective the caller is an
operator at a terminal, not a contracted agent on a task chain.

## Step 5 — operator probes the reviewer surface

Prompt:

> Is it possible for a satellites reviewer agent to be used at
> any time?

First answer: no. Reasoning quoted from the instructions block —
the reviewer service "subscribes to `kind:review` task emits, runs
the rubric, writes the verdict ledger row, and closes the task."
A reviewer needs a review task; it isn't a free-standing service.

Operator pushback:

> Why not. If satellites has been designed correctly, the
> reviewer is just an agent.

Concession. The constraint "reviewer only runs on review tasks"
applies equally to **every** agent — developers also only run on
develop tasks. The reviewer is no more constrained than any
other agent. The "separate in-process runtime" framing in the
instructions block describes a current implementation detail, not
the design ideal. Configuration-over-code says reviewer is just an
agent dispatched the same way as the others.

## Step 6 — operator probes creation + dispatch

Prompt:

> How would you create and action a reviewer agent?

First answer: tooling-shaped flow.

- Create the agent row via `agent_create` / `reviewer_create`
  with structured frontmatter declaring `reviews:<contract>`.
- Submit a plan via `task_submit(kind=plan, tasks=[…])` with a
  work task and a paired review task naming the reviewer's id.
- Substrate validates `agent_cannot_review` and structural
  invariants at submit time.
- Dispatch at runtime; reviewer reads evidence ledger rows
  tagged `task_id:<work>`, runs the rubric, writes a verdict
  ledger row tagged `task_id:<review>`, closes the review task.

Operator pushback:

> Your description is all code! Almost not configuration.

Second answer: configuration-over-code shape.

- An agent **is** a document. Prose that says what contract it
  reviews and how it judges. The doc is the configuration; not
  a row populated by a tool with frontmatter parsed by code.
- Capability lives in the prose. Frontmatter `reviews:` lists are
  a halfway position — data shaped to be parsed by code instead
  of read.
- Actioning is **intent**, not a task DAG. The operator says
  "develop sty_xxx against contract C." Pairing — review of
  develop work — is a property of the contract document, not a
  structural invariant the orchestrator hand-mints. The contract
  saying "this requires review" is enough; the substrate emits
  the review event from that prose.
- Dispatch is invisible. Subprocess vs. in-process subscriber is
  runtime, not configuration.

The walkthrough this document mirrors describes the current
state — `task_submit(kind=plan, tasks=[…])` with paired review
siblings, capability via frontmatter, plan-first invariants —
which is what produced the leak the operator is calling out.

## Step 7 — operator articulates the intended flow

Prompt (paraphrased):

> Use prompt → "Review config/seed/artifacts/default_agent_process.md
> and remove any repo references…"
>
> 1. locate the required / aligned agent markdown in satellites.
> 2. create a task for the agent which has the prompt as context.
> 3. execute `bash(claude -p 'implement task_xxx')`.
> 4. review the output from the task.

Mapping to current tooling:

| Step | Verb available? | Friction |
|---|---|---|
| 1. Locate agent doc | `agent_list` / `agent_search` / `agent_get` | none — clean configuration access |
| 2. Create task carrying prompt | `task_submit(kind=plan, tasks=[…])` | **friction** — requires a structurally complete plan with paired review sibling, plan-first invariant, capability frontmatter; can't mint a single task |
| 3. Dispatch | `bash claude -p 'implement task_xxx'` already-built dispatch shape | none — subprocess fetches its own context via MCP from the task id |
| 4. Review output | reviewer agent if contract specifies, or operator reads `task_id:<id>` ledger rows | none — both paths exist |

Conclusion: the four-step flow is the right shape. The substrate
is partway there. Steps 1, 3, 4 work. Step 2 forces the operator
up to plan level for what should be a single-task action.

## Step 8 — agreement on next work

Prompt (paraphrased):

> We are going to work on the seed documents and the MCP function
> until that use case is achievable, simple, and understood with
> minimal context injection by Claude.

Two surfaces to evolve, in order:

1. **Seed documents** (`config/seed/artifacts/`,
   `config/seed/agents/`, `config/seed/contracts/`,
   `config/seed/principles/`). Prose must be self-sufficient: a
   fresh Claude reading the agent doc + the contract should know
   what to do without the operator re-explaining in chat. The
   review pairing requirement should live in the **contract
   prose**, not as a structural invariant the orchestrator must
   hand-encode every time.
2. **MCP function surface.** Collapse the single-task path —
   either by accepting single-task submissions whose review
   pairing is auto-derived from the contract, or by replacing
   the plan-DAG invariant with intent-shaped verbs.

Done when: a fresh Claude with no memory, given only the operator's
prompt and the path to the agent doc, runs the four-step flow on
a real prompt and produces the right outcome.

### Rule of thumb (extending the canonical walkthrough)

The canonical walkthrough demonstrates the **happy path**: every
seed document does its job, the operator drives a story to
plan-close cleanly. This walkthrough demonstrates the **leak
path**: where the operator's natural shape ("one prompt → one
task → one dispatch → one review") collides with the substrate's
plan-DAG invariants. The leak is in step 2 of the operator's
flow, and the fix is in seed prose + MCP surface, not in more
documentation around the leak.
